**Where the agent was wrong, and how I noticed.** 

Few times after implementing one of requirements from SPEC.md there were errors catch by typescript compiler or written tests. Those were commits:
1. `accept updates over HTTP and persist them transactionally` - tsc error
2. `supersede pending jobs covered by a newer update [SYNC-04]` - committed while the SYNC-04 test was failing
3. SYNC-04 failed due to wrong test `only the covered chunks of a multi-chunk update are superseded` which asserted wrong chunk boundary. Fixed after test case review.
4. SYNC-11 test hang the whole run which is obviously an issue that was analyzed and fixed. 
5. API-05 - failed unit test `update status from job states`: an update with no jobs derived as synced
6. SYNC-05 - failed due to corrupted body which was fixed by "text/plain" mime type
7. SEC-06 - failed test `a response body is read only up to the cap`. Was fixed by using custom `fetch` whose stream counts how many chunks were pulled and whether it was cancelled
8. SYNC-16 - failed test `a backlog larger than one minute's budget drains without a single 429` due to rate limiter was tuned to exactly the portal's limit, 30 calls per 60 seconds, with no margin. Clear architectural flaw that was fixed

**Left out, in the order I would do them.** 

1. Re-queue endpoint for failed jobs. Today a job that gave up is retried only with an UPDATE on the table. First because support hits this gap first and it is a small change
2. Shared rate limiter. The window is in-process, so two instances would each claim the whole 30 calls a minute. The claim query is already multi-instance safe; this is the one thing blocking a second replica
3. Circuit breaker. When the portal is down, every slot still spends budget on failing calls. A breaker that opens after N consecutive unavailable outcomes sits next to the limiter and in the worker's outcome switch
4. Day-level merge. Removes a known trade-off that one failing accommodation blocks its own later updates but only after a redesign. The current ordering is correct for the common case
